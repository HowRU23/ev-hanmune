# Workflow: 새 가이드(FAQ) 콘텐츠 추가하기

## 목표
"전기차 한눈에" 웹사이트에 새로운 가이드 글(FAQ 형태)을 추가한다.

## 배경: 왜 FAQ 형태인가
2026-09-15 EV3 오너 단톡방 16.5개월치 대화 정량 분석(`docs/오너방-질문분석.md` 참고) 결과, 사람들은
"전기차 입문 지식"보다 "지금 내 상황에 대한 구체적 질문"을 더 많이 찾는다는 게 확인됨.
그래서 이 사이트는 교과서식 가이드가 아니라 **질문 하나 = 글 하나**인 FAQ 구조로 간다.
카테고리 분류가 안 좋으면 사람들이 페이지 대신 그냥 단톡방에 물어보고 끝나므로, 분류·검색이 핵심이다.

## 언제 쓰나
사장이 "OO 주제로 글 하나 써줘" 또는 "OO 질문에 대한 답 추가해줘"라고 요청할 때.

## 주제 목록 기준
`내용자료.txt`(프로젝트 루트)가 사장이 관리하는 마스터 주제 목록이다. 새 글을 시작하기 전에 이 파일을 먼저 읽고, 거기 적힌 주제 범위 안에서 작성한다. 목록에 없는 새 주제를 요청받으면, 작성 전에 `내용자료.txt`에도 추가할지 사장한테 확인한다. 이 파일은 사장이 직접 갱신하는 살아있는 목록이므로, 매번 다시 읽고 최신 상태를 기준으로 판단할 것.

**사이트는 원칙적으로 특정 차종(예: EV3) 이름을 명시하지 않는다.** 충전/배터리 관리처럼 전기차 공통 내용은 일반화해서 쓰고, 특정 모델명을 콕 집어 언급하지 않는다.

**예외:** 트림/옵션명(에어·어스·GT라인 등)처럼 내용 자체가 특정 차종에 고유한 주제는 그 차종명을 명시한다. 억지로 일반화하면 부정확해지기 때문. 이런 글은 제목이나 카테고리에서 "OO 차종 한정" 티가 나게 써서, 다른 차종 오너가 헷갈리지 않게 한다.

## 콘텐츠 소싱 규칙 (중요)
- **답변 내용은 카카오톡 단톡방 원문을 인용하지 않는다.** 단톡방 데이터는 "어떤 질문이 많이 나오는지" 우선순위 판단에만 쓴다.
- **기아 공식 오너스 매뉴얼(ownersmanual.kia.com)을 우선 근거로 활용한다.** 매뉴얼에 있는 내용이면 그걸 기준으로 쓰고, 가능하면 출처 링크를 본문에 남긴다.
- 매뉴얼에 없는 내용(요금, 카드 할인, 커뮤니티 노하우 등)은 웹 검색으로 직접 검증한 뒤 작성한다. 확인 안 된 카더라는 쓰지 않는다.

## 리스크 문구 배제 규칙 (매우 중요, 2026-09-15 추가)
**확실하지 않으면, 아예 그 얘기를 꺼내지 않는다.** "이건 이렇게 유지된다", "이런 경우엔 이렇게 된다"처럼 예외나 변동 가능성이 있는 규칙성을 단정적으로 서술하지 않는다. 리서치로 근거를 찾았더라도, 예외 케이스가 만에 하나 있을 수 있다면 그 문장 자체를 쓰지 않는 게 맞다.

- 예: "보조금은 한 번 책정되면 그 해 동안 유지됩니다" 같은 문장은 대체로 맞더라도 쓰지 않는다. 드물게라도 틀릴 수 있는 주장은 사이트에 올리지 않는다.
- 판단 기준: 이 문장이 훗날 예외 사례로 틀린 것으로 밝혀지면 곤란한가? 그렇다면 아예 빼고, 꼭 필요하면 "정확한 내용은 OO에서 확인하세요"로 링크아웃한다.
- 이 규칙은 "확인된 사실만 쓴다"보다 한 단계 더 보수적이다. 확인된 사실이어도, 예외가 있을 수 있는 규칙성 주장은 리스크이므로 제외한다.
- 공식 사이트로 보여야 하는 페이지이기 때문에, 이 기준으로 모든 문구를 검토해야 한다.

## 글쓰기 스타일 규칙 (매우 중요)
- **em dash(—)를 절대 쓰지 않는다.** 문장 어디에도, 마크다운 본문은 물론이고 사이트의 모든 UI 텍스트(컴포넌트, 버튼, 메타 설명 등)에도 금지. AI가 쓴 글이라는 티가 가장 크게 나는 특징이라 사장이 명시적으로 금지함.
- 대신 마침표로 문장을 끊거나, 쉼표·콜론(:)으로 잇거나, 아예 문장을 다시 쓴다. 나열에는 `·`(가운뎃점)를 쓴다.
- 글을 쓰거나 코드를 수정할 때마다 `—`가 들어가지 않았는지 스스로 확인할 것.

## 카테고리 체계 (2026-09-15 개편)
아래 중 하나를 `category`에 사용. 새 카테고리가 꼭 필요하면 사장한테 먼저 확인. 도구(`/tools/*`, 보조금·유지비 계산기 등)는 이 분류 대상이 아니다. 이 체계는 원래 7개(구매/충전/관리/주행/보증/보험/용품)였다가, 글이 몇 개 안 되는 초기 단계에서는 너무 잘게 쪼개져 있다는 사장 피드백으로 5개로 통합함. "비용·혜택"은 임시 명칭이라 나중에 더 나은 문구가 나오면 바뀔 수 있음.

| 카테고리 | 예시 주제 |
|---|---|
| 충전·배터리 | 완속/급속 차이, 충전 요금, 카드, 집밥 구조, 배터리 관리/컨디셔닝, 충전 괴담 해석 |
| 주행·전비 | 주행거리/전비 정확도, 회생제동, 아이페달 |
| 트림·옵션 | 트림/옵션 선택, 빌트인캠 등 옵션 관련 이슈 |
| 차량관리 | 무상보증 연장(기아멤버스) |
| 비용·혜택 | 보험 할인(운전점수 활용), 신용카드 할인. 보조금·유지비처럼 도구로 만든 건 여기 안 들어감 |

**오토큐/정비소 관련 주제는 이 사이트에서 다루지 않는다.** 별도 프로젝트 "오토큐 한눈에"에서 진행 중이며, 추후 연동하거나 트랙을 나눈다.

## 검토 프로세스 (중요, 2026-09-15부터 적용)
**바로 `content/guides/`에 파일을 쓰지 않는다.** 리서치 오류가 사장 검토 없이 그대로 사이트에 올라가는 문제가 있어서, Notion에 중간 검토 단계를 둔다.

검토 데이터베이스: [전기차 한눈에 콘텐츠 검토](https://app.notion.com/p/b27d360f0bdc43a1b72dd9669f98c1d2)

속성: 슬러그(파일명으로 쓸 영문 슬러그) / 카테고리 / 상태 / 출처 / 검토메모

상태 흐름: 리서치중 → 초안 → 검토요청 → (문제 있으면 수정필요, 고치고 다시 검토요청) → 승인완료 → 게시됨

절차:
1. 공식 매뉴얼·웹검색으로 근거를 모은다 (콘텐츠 소싱 규칙 그대로 적용).
2. Notion 데이터베이스에 새 페이지를 만든다. 제목(질문형)·설명·요약(TL;DR)·본문을 페이지 안에 다 쓰고, 속성에 슬러그/카테고리/출처를 채운다. 상태는 "검토요청"으로 둔다.
3. 사장한테 검토 요청 사실을 알린다.
4. 사장이 페이지 댓글이나 검토메모로 피드백을 주면, 상태를 "수정필요"로 바꾸고 반영한 뒤 다시 "검토요청"으로 되돌린다.
5. 사장이 승인하면(상태를 "승인완료"로 바꾸거나 명시적으로 승인한다고 말하면), 사이트에 반영하기 직전에 **최종 검증 3종 세트**를 거친다. 이 검증을 통과해야 "게시됨"으로 바꾸고 아래 "단계"를 진행한다.

## 최종 검증 3종 세트 (2026-09-15 추가, 사장 승인 후 게시 직전 필수)
Notion에서 사장이 검토/승인한 글이라도, 사이트에 올리기 직전에 아래 3가지를 다시 한번 반드시 확인한다. 이건 사장 승인을 대체하는 게 아니라, 승인된 내용이 실제로 맞는지 마지막으로 한 번 더 점검하는 단계다.

1. **신빙성·신뢰성 교차 검증**: 본문에 있는 사실 주장 하나하나를 웹검색으로 다시 확인한다. 한 곳의 출처만 믿지 말고, 가능하면 서로 다른 출처 2곳 이상에서 같은 내용을 확인한다.
2. **리스크 재점검**: 리스크 문구 배제 규칙 기준으로 본문을 다시 훑는다. 예외 있을 수 있는 단정 문장이 남아있지 않은지 확인한다.
3. **제조사 매뉴얼 우선 확인**: 가능한 부분은 제조사 공식 매뉴얼(예: ownersmanual.kia.com)을 근거로 삼았는지 확인한다. 매뉴얼에 없는 내용은 신뢰도 높은 출처(정부기관, 법령, 공신력 있는 언론/기술 자료)로 대체 검증한다.

이 검증에서 문제가 발견되면, 사장이 승인했더라도 그 사실을 먼저 사장한테 알리고 고친 뒤 진행한다. 조용히 넘어가지 않는다.

2026-09-15에 이미 써뒀던 글 4개(입문 가이드, 트림 가이드, 빌트인캠, 회생제동/아이페달)는 검토 전 상태로 `content/_pending-review/`로 옮겨뒀다. 이 폴더는 사이트에 노출되지 않는다(`content/guides/`만 스캔함). Notion에서 승인되면 여기서 `content/guides/`로 옮기면 된다.

## 단계 (승인된 콘텐츠를 사이트에 반영하는 방법)
1. `content/guides/` 폴더에 새 마크다운 파일 생성. 파일명은 Notion에 적어둔 슬러그와 동일하게 (예: `winter-range-tips.md`).
2. 파일 맨 위에 frontmatter 작성:
   ```
   ---
   title: "질문형 제목 (예: 100% 완충해도 배터리에 안 좋나요?)"
   description: "한 줄 요약 (카드에 노출됨)"
   category: "위 카테고리 체계 중 하나"
   readTime: "예상 읽는 시간 (예: 6분)"
   publishedAt: "YYYY-MM-DD"
   popular: true   # 자주 찾는 질문으로 상단에 고정하고 싶을 때만 추가 (선택)
   summary:
     - "결론 한 줄 (핵심 요약 박스에 노출됨)"
     - "결론 한 줄 더"
     - "3~4개 정도가 적당"
   ---
   ```
   - `title`은 실제로 사람들이 물어보는 말투에 가깝게 질문형으로 쓴다. ("전기차 배터리 관리법" 대신 "전기차 배터리, 어떻게 관리해야 오래 가나요?")
   - `summary`는 필수. 본문을 안 읽어도 결론만 보고 넘어갈 수 있도록 핵심을 3~4줄로 압축한다. 상세 페이지 상단에 강조 박스로 자동 표시된다.
3. frontmatter 아래에 본문을 마크다운으로 작성. `##` 소제목 단위로 구조화.
4. **글이 길어질 것 같으면(주제가 2개 이상 섞이면) 쪼갠다.** 질문 하나 = 글 하나 원칙. 한 페이지에 여러 소주제를 욱여넣지 말 것. `summary` 박스로도 해결 안 될 만큼 길어지면 애초에 다른 글로 나눠야 하는 신호다.
5. 저장만 하면 끝. 홈페이지(`/`)와 가이드 목록(`/guides`)에 자동으로 노출되고, 검색·카테고리 필터에도 자동으로 잡힌다. 상세 페이지(`/guides/파일명`)도 자동 생성되며 코드 수정은 필요 없다.
6. `npm run dev`로 로컬에서 확인 (http://localhost:3000).

## 결과물
- 새 글이 홈페이지 "최신 가이드" 섹션, `/guides` 검색/필터 목록에 나타남
- `popular: true`면 `/guides` 상단 "많이 찾는 질문"에도 고정 노출
- `/guides/{슬러그}` 경로에서 전체 글 확인 가능

## 문제 생기면
- 카드에 글이 안 보임 → frontmatter 형식(따옴표, 들여쓰기) 확인
- 본문이 깨져 보임 → 마크다운 문법 확인 (제목은 `##`, 리스트는 `-`)
- 검색이 안 잡힘 → 검색은 title/description 텍스트만 기준으로 매칭됨. 사람들이 실제 쓸 법한 단어가 description에 들어있는지 확인
